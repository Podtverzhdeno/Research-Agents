## 2. Один основной прикладной сценарий для совместной продуктовой проверки

**Клиент:** юрлицо-покупатель заказывает оборудование, агент готовит запрос на гарантию оплаты на **8 млн ₽ / 90 дней** (*примерная тестовая сумма и срок, не условия банка*).

| Шаг | Что реально делает банк | ФБС, которая владеет именно этой функцией | Негативный тест |
|---|---|---|---|
| 1 | Публикует сведения и условия гарантийного продукта в корпоративном агентном канале | **2.1.3** | Не обещать автоматическую выдачу по опубликованному тарифу |
| 2 | Допускает к цифровому каналу только разрешённую функцию | **2.2**, подключение сервиса **5.4.1** | Чужой API scope не даёт доступа к заявке |
| 3 | Устанавливает юридическое лицо и разрешение его представителя | **3.1.1**, **3.1.9** | Запросить разрешено; подписать — запрещено → отказ при акцепте |
| 4 | Идентифицирует экземпляр агента (если владелец кода подтвердил 3.1.15) | **3.1.15** *проектная*, ключи **7.7.2.1.3.2** | Старый/подменённый credential заблокирован |
| 5 | Помогает продавцу банка согласовать нестандартные параметры продукта | **3.3.3** | Без внутренних согласований нет binding offer |
| 6 | Вычисляет согласованную банковскую комиссию | **4.1.5** | Цена не меняется после согласия без основания |
| 7 | Готовит и согласует действительный банковский договор | **4.1.2**, подпись **7.11.1** | Обязательства не возникают из одного текстового намерения агента |
| 8 | После необходимых юридических/рисковых проверок оформляет гарантию | **4.1.22.2** | Несовпавший принципал/бенефициар/сумма → отказ |
| 9 | Проверяет банковские данные, AML и возвращает законный статус | **6.1.5/6.1.6/6.1.7/6.1.10/6.1.11**, **7.5.1** | Подписанный акт не равен поставке; чужим агентам нет клиентского досье |

**Важно:** оценка риска гарантийного обязательства, юридический контроль, политика лимитов и право подписи — дополнительные обязанности профильных владельцев, **не исчезают** от наличия этих ФБС. Не требуется запускать все перечисленные технологические улучшения как условие существования каждой заявки. Провести один CJM со step-by-step evidence и E2E.

**Банковская ценность:** комиссия и сокращение cost-to-serve только при доказанном сравнении с обычной гарантийной заявкой; качество не измерено в PR.

## 3. Три отдельные коммерческие опции — НЕ сливать в один выдуманный продукт

| Кандидат | Прикладная операция | Правильная ФБС | Без чего НЕ запускать |
|---|---|---|---|
| **Внешние счета компании** | Казначейский агент компании получает разрешённые сведения и при поддержке внешнего банка инициирует допустимую операцию по открытому там счёту | **4.1.12**, мандат 3.1.9 | Договор/согласие, partner API, полномочие на удалённое действие, понятная экономика |
| **Эскроу под приёмку** | Деньги покупателя депонированы и передаются по законному условию и юридически достаточным доказательствам | **4.1.24**, документы/данные 6.1.6/6.1.7 | Договорная схема и допустимое условие выплаты; stop при конфликте; не arbitrary N траншей |
| **Корпоративная карта агента** | Банковская карта/токен компании на конкретный расход/сумму/получателя | **4.1.8.1**, 3.1.9 | Права, управляемый token, проверка merchant controls, отсутствие двойной оплаты |

**Не основные ставки в общем корпоративном CJM:** `4.1.14.2` выпуск **собственных** бумаг банка, `4.1.1` распоряжения на сделки с финансовыми инструментами, `4.1.14.4` торговля ими; это **сегментный самостоятельный use-case**, не обычный банковский платёж. `4.1.6` исходно «Без изменений»; депозитная агентная схема лишь отдельный change request. Клиентское кредитование/факторинг и полноценный FX owner **не входят в 54**; код не придумывать.

## 5. Сводный предметный реестр решений 54/54

**Формат:** исходный код/название/исторический тип → прикладное действие из [PR #49](https://github.com/Podtverzhdeno/Research-Agents/pull/49) → критерий из второго прохода [PR #48](https://github.com/Podtverzhdeno/Research-Agents/pull/48) → **исследовательская диспозиция**, не утверждение банка.

|---|---|---|---|---|---|
| `2.1.3` Онбординг продуктов в канал | Доработка | Агент закупщика запрашивает банковскую гарантию для заказа оборудования | Банк отдаёт в агентный канал карточку гарантии: лимиты применимости, документы, тариф и срок ответа; заявку принимает через API | Доля корректно принятых RFQ; ответы не содержат неутверждённых условий. | AGENT CHANNEL FOR PRODUCT |
| `2.1.4` Управление настройкой электронной части канала | Доработка | Закупочный агент начал заявку в ERP, но требуется подпись директора в ДБО | Сохранять единый номер заявки и подставлять уже проверенные данные при передаче человеку, затем вернуть статус агенту | Один ID заявки после трёх повторных запросов. | CJM-DEPENDENCY |
