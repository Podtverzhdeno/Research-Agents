# Финальная редакционная резолюция 54 ФБС: 30 споров, портфель 2031–2041

**29.10.2026 — EDITORIAL_DECIDED / BANK_APPROVAL_OPEN.** Источник границ — последний функциональный реестр пользователя (54/54, включая 3.1.15). Исходные полные определения из внутреннего XLSX **не публиковались** в GitHub; построчный анализ/30 решений/Excel пользователь получил приватными файлами.

## Главная поправка консилиума
**Нельзя называть прежний ТОП-7 семью независимыми продуктами.** Объединяем `4.1.1` (приём, проверка, исполнение распоряжения) и `4.1.10.1` (холдирование и фактические внутрибанковские расчёты) в **ОДИН** клиентский CJM многостороннего условного B2B-расчёта. Техническую/юридическую «атомарность» для произвольных N сторон **не обещаем**. `7.5.1` AML — отдельная защитная инвестиция, не платный банковский продукт.

**Три основных продукта для исследования:** (1) условные агентные расчёты `4.1.1 + 4.1.10.1`; (2) гарантия для сделки автономных компаний `4.1.22.2`; (3) мультибанковское казначейство `4.1.12`. **Два условных продукта:** escrow `4.1.24` и эмиссия новых законных цифровых прав `4.1.14.2`. **Защита:** `7.5.1` AML.

**Девять несамостоятельных фундаментов:** `2.1.3`, `2.2`, `3.1.9`, `3.1.15`, `5.4.1`, `6.1.6`, `6.1.7`, `6.1.11`, `7.7.2.1.3.2`.

## 30 закрытых редакционных вопросов (сгруппированы)

| Группа спора | Принятое редакционное решение |
|---|---|
| Двойной счёт 4.1.1/4.1.10.1 | Два процесса **одного продукта**; финальность отдельно от распоряжения |
| Всеобщий atomic netting | Отказать без действительной схемы холдирования и подтверждённой finality |
| «Оплатить approved invoice» как прорыв 2040 | Исключить: аналог agent payment уже пилотировался Visa/BILL/Billtrust в октябре 2026 |
| Просто цифровая банковская гарантия | Недостаточно: цифровая ICC–Swift API гарантия уже была в январе 2026 |
| A2A сам выдаёт/изменяет гарантию | Запретить: обязательство банка и изменения по действительным правилам |
| Гарантия, обеспечение, escrow | Раздельные продукты/договоры/риски; не переносить обязательства между ФБС |
| Escrow «по мнению ИИ» | Отклонить: только договорное основание выплаты и режим спора |
| Произвольные части escrow | Не обещать без отдельно действительной договорной конструкции |
| Мультибанковский счёт клиента | Только при фактическом праве и интеграции внешнего банка |
| Мультибанк автоматически выгоден банку | Каннибализация остатков учитывается как отрицательный вклад |
| Выпуск ЦФА = токенизация старой бумаги | Недостаточно для 2036: нужен новый профиль законного экономического права |
| ЦФА = платёжные деньги | Не выводить из названия; отдельно проверить применимое право и исключения |
| Выпуск vs сделки vs хранение цифрового актива | Разные ФБС: 4.1.14.2, 4.1.14.4 и 4.1.13.6.2 |
| Глобальное залоговое право по токену | Не предполагать title/priority/double pledge без правовых оснований |
| Канал vs полномочия vs agent ID vs PKI | `2.2`, `3.1.9`, `3.1.15`, `7.7.2.1.3.2` разделяются |
| Идентифицированный runtime = безопасная модель | Нет: подтверждение происхождения не доказывает корректность решения |
| Данные ERP = юридически подтверждённая поставка | Нет: `6.1.6/6.1.7/6.1.11` собирают, нормализуют, согласуют события |
| Согласие клиента = распространение данных | `3.1.10` и `6.1.10` разные права/процессы |
| ИТ-мониторинг = AML | `5.2.6` и `7.5.1` разделены |
| Клиентская факторинговая ДЗ = бухгалтерская ДЗ банка | Нет: `7.2.2.3` относится к банку |
| Физические наличные операции = цифровые деньги | Нет: штатная cash-функция с физическим подтверждением |
| Межбанковская атомарность | Дальний опцион, требуются реальный расчётный коридор/fallback |
| Формальные согласования «всех сторон» | Не получены: смоделированное исследование GPT-6 не заменяет Legal/Risk/Product/FBS/ИБ |

Остальные споры из **30** сведены к тем же veto: ни один интерфейс/AI-сообщение не создаёт самостоятельно юридическое обязательство, банковское право или подтверждённую стоимость продукта. Подробный построчный журнал 30/30 в приватном артефакте.

## Что нужно, чтобы банк мог сказать «утверждено»
1. Реальная Product/P&L оценка `incremental risk-adjusted contribution` к лучшей текущей услуге (включая каннибализацию).
2. ФБС owner ACK точно на свои действия; не копировать обязанность соседней ФБС.
3. Legal заключение под конкретный договор гарантии, escrow, режим ЦФА, доступ к внешнему банку.
4. Credit Risk / AML / sanctions, включая ложные блокировки.
5. Сквозной E2E: общий бюджет/отзыв, double submit, ложное доказательство, ошибка бенефициара, неизвестный финальный статус, сбой стороннего банка.
6. Клиентское подтверждение реальной боли и willingness-to-pay.

**30/30 споров разрешены как редакционные противоречия. Ни одно из них не даёт оснований заявить `BANK_APPROVED`.** Единственный внешний gate — [issue #47](https://github.com/Podtverzhdeno/Research-Agents/issues/47).
