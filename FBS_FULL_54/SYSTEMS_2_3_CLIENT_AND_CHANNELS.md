# Системы 2–3: Каналы и клиентский опыт — полная предметная проработка (13/54)

**Срез:** 28.10.2026. **Источник статуса/идеи:** [TRACEABILITY_54_BASELINE_VS_RESEARCH.md](../TRACEABILITY_54_BASELINE_VS_RESEARCH.md). **Гипотезы ниже — новые исследовательские предложения**, не факты исходного HTML и не одобрение владельцев ФБС. Роли P/C/B/0 — отдельная шкала, отличная от исторических 40/3/11.

## 2.1.3 — Онбординг продуктов в канал

**Исходный тип:** Доработка. **Идея из HTML:** AI-платформы как канал продаж: контроль опыта, правила интеграции. **Роль в GitHub:** B. **Редакционное действие:** Усилить / P0-канал.

**Прикладной сценарий 2031–2036.** Закупочный агент юрлица запрашивает у банка структурированную котировку гарантии или финансирования и получает цену, ограничения, срок актуальности, ссылку на юридически значимые условия.

**Ценность корпоративному клиенту.** Клиент сравнивает реальную полную стоимость, не обращаясь в 10 банковских кабинетов; отказ объясняется машинно.

**Банковский эффект.** Банк получает право участвовать в RFQ внешних платформ и измеряет выигранные сделки, но машинный доступ может сжимать маржу.

**Граница и негативный тест.** Не обещать безусловный кредитный офер при неподтверждённых лимитах, мандате или риске; не строить конкурирующую ERP ради контроля входа.

**Проверяемые показатели (без вымышленных чисел).** Agent RFQ→валидная котировка→выбор→открытая услуга; чистый доход и доля выигранных котировок по рисковым сегментам.

**Решение по ФБС.** Сохранить исходную доработку; повысить исследовательский приоритет B→C при сценарии внешних агентных закупок.

## 2.1.4 — Управление настройкой электронной части канала

**Исходный тип:** Доработка. **Идея из HTML:** Интеграция классических каналов с агентной инфраструктурой. **Роль в GitHub:** B. **Редакционное действие:** Конкретизировать.

**Прикладной сценарий 2031–2036.** Оператор компании переключает заявку агент↔ДБО↔человек, сохраняя один case_id, действующие данные и причины остановки.

**Ценность корпоративному клиенту.** Можно завершить начатый агентом сценарий без повторной подачи документов и потери контрольной точки.

**Банковский эффект.** Банк сокращает брошенные заявки и обращения; сохраняет доступный неагентный канал.

**Граница и негативный тест.** Недопустим неявный downgrade контроля при переводе из A2A в ручной интерфейс; version pinning условий и полномочий.

**Проверяемые показатели (без вымышленных чисел).** Доля восстановленных заявок; ошибочный повтор операции; число повторных вводов и зависших состояний.

**Решение по ФБС.** Доработка канала, не отдельный продаваемый продукт.

## 2.2 — Управление доступом к каналу

**Исходный тип:** Доработка. **Идея из HTML:** Идентификация агентов и их привилегии в каналах. **Роль в GitHub:** C. **Редакционное действие:** Обязательный допуск / P0.

**Прикладной сценарий 2031–2036.** Агент корпоративного клиента обращается к конкретному банковскому API с атрибутами юрлица, роли, мандата, получателя и вида операции.

**Ценность корпоративному клиенту.** Клиент делегирует без выдачи логина сотрудника, отбирая доступ по задаче.

**Банковский эффект.** Банк ограничивает операционные потери и защищает каналы от несанкционированных действий.

**Граница и негативный тест.** Проверять every request, scope/tenant/expiry, revoke; запрет replay и обхода через старую сессию; технический доступ не равен полномочию заключать кредит.

**Проверяемые показатели (без вымышленных чисел).** Unauthorized pass rate (цель ноль в тестах), время отзыва, число false denies, аудит deny reasons.

**Решение по ФБС.** Сохранить доработку; обязательный security-gate, не банковская KYC-функция сама по себе.

## 3.1.1 — Идентификация клиента

**Исходный тип:** Доработка. **Идея из HTML:** Связка идентификации клиента с агентом при регистрации агента. **Роль в GitHub:** B. **Редакционное действие:** Развести субъектов.

**Прикладной сценарий 2031–2036.** При регистрации корпоративного агента банк проверяет юрлицо/представителя и лишь затем связывает agent instance с подтверждённым клиентом.

**Ценность корпоративному клиенту.** Сотрудники не проходят новую идентификацию на каждое действие доверенного агента.

**Банковский эффект.** Банк сохраняет неизменного ответственного клиента и полный KYC-профиль.

**Граница и негативный тест.** Не считать агента новым самостоятельным клиентом или владельцем счёта; корпоративный KYC и UBO остаются.

**Проверяемые показатели (без вымышленных чисел).** Доля корректных principal→agent связок; кейсы orphaned identity; число повторных KYC-процедур.

**Решение по ФБС.** Исходная доработка; не создавать отдельную клиентскую правосубъектность ИИ.

## 3.1.2 — Аутентификация клиентов

**Исходный тип:** Доработка. **Идея из HTML:** KYC агентских сценариев, непрерывная проверка доверия вместо статической аутентификации. **Роль в GitHub:** B. **Редакционное действие:** Развести аутентификацию и права.

**Прикладной сценарий 2031–2036.** Агент проходит аутентификацию ключом и подтверждением среды исполнения; банк отдельно сверяет мандат перед значимым действием.

**Ценность корпоративному клиенту.** Доступ без передачи личных паролей бухгалтера и без CAPTCHA для машинного клиента.

**Банковский эффект.** Снижается credential sharing и риск подмены доверенного агента.

**Граница и негативный тест.** Токен агента не доказывает полномочие; ротация ключей, proof-of-possession, runtime replay, step-up approval.

**Проверяемые показатели (без вымышленных чисел).** Доля успешных impersonation тестов (цель ноль), latency step-up, число украденных long-lived секретов.

**Решение по ФБС.** Исходная доработка: не называть идентификацию агента просто «KYC».

## 3.1.7.1 — Основные данные клиента

**Исходный тип:** Доработка. **Идея из HTML:** История поведения агентов клиента, рейтинги и оценка доверия. **Роль в GitHub:** B. **Редакционное действие:** Досье агента у клиента.

**Прикладной сценарий 2031–2036.** В карточке юрлица вести версионированные связи с агентами, владельцами, контактами, разрешёнными ролями, фактами отзыва и историей.

**Ценность корпоративному клиенту.** Администратор компании видит, какие агенты сейчас уполномочены, и может безопасно завершать доступ.

**Банковский эффект.** Банк снижает обслуживание невидимых/осиротевших автоматизаций.

**Граница и негативный тест.** Не строить непрозрачный «рейтинг благонадёжности ИИ» без проверенной модели и обжалования; данные агента не подменяют профиль юрлица.

**Проверяемые показатели (без вымышленных чисел).** Время выявления orphaned agent; доля актуальных записей; доля отказов по устаревшему мандату.

**Решение по ФБС.** Исходная доработка, не новая функция KYA в обход 3.1.15.

## 3.1.9 — Управление полномочиями клиента

**Исходный тип:** Доработка. **Идея из HTML:** Мандаты: что можно, кому, на какую сумму и срок; проверка каждого действия. **Роль в GitHub:** C. **Редакционное действие:** P0: экономические мандаты.

**Прикладной сценарий 2031–2036.** Финансовый директор разрешает агенту запросить котировки и оплачивать только определённых поставщиков до бюджета X за период, но запрещает открывать новый кредит.

**Ценность корпоративному клиенту.** Формальное делегирование без постоянного ручного участия, с возможностью срочного отзыва.

**Банковский эффект.** Банк контролирует рисковую волю корпоративного принципала до принятия обязательств.

**Граница и негативный тест.** Отдельные права на просмотр, сравнение, акцепт оферты, распоряжение, кредит/гарантию; revocation race, субделегирование и легальные подписи.

**Проверяемые показатели (без вымышленных чисел).** Процент операций с действительным мандатом; latency revoke→block; предотвращённые превышения бюджета и false denies.

**Решение по ФБС.** Сохранить Доработку; prerequisite GATE ко всем денежным агентным сценариям.

## 3.1.10 — Управление согласиями клиента

**Исходный тип:** Доработка. **Идея из HTML:** Согласие на обработку данных агентом-представителем, объём прав, срок, отзыв. **Роль в GitHub:** B. **Редакционное действие:** Согласия и законное раскрытие.

**Прикладной сценарий 2031–2036.** Компания разрешает банку отправить конкретному проверяющему статус оплаты/приёмки без раскрытия всего договора и истории переговоров.

**Ценность корпоративному клиенту.** Получает прозрачный доступ к данным с отзывом разрешений.

**Банковский эффект.** Банк уменьшает риск недопустимого раскрытия банковской/коммерческой тайны.

**Граница и негативный тест.** Нужно правовое основание обмена и purpose-based policy; отзыв не аннулирует уже законно произведённое раскрытие; минимизация данных.

**Проверяемые показатели (без вымышленных чисел).** Доля доказательств с действующим правовым основанием; число over-sharing инцидентов; время обработки отзыва.

**Решение по ФБС.** Доработка согласий; техническая выдача остаётся в 6.1.10.

## 3.1.15 — Идентификация агента

**Исходный тип:** Новая. **Идея из HTML:** KYA: паспорт агента, децентрализованный идентификатор. **Роль в GitHub:** C. **Редакционное действие:** Исходная НОВАЯ / P0 agent identity.

**Прикладной сценарий 2031–2036.** При подключении агент предъявляет подписываемый реестровый идентификатор с привязкой к юрлицу, владельцу, среде выполнения, версии и ключу.

**Ценность корпоративному клиенту.** Можно отличить авторизованную копию агента от подменённого экземпляра.

**Банковский эффект.** Банк подтверждает сторону машинного взаимодействия и может блокировать скомпрометированную версию.

**Граница и негативный тест.** Стандарты identity ещё меняются; не объявлять DID обязательным или достаточным; credential ≠ экономический мандат; runtime attestation может отсутствовать.

**Проверяемые показатели (без вымышленных чисел).** Identity coverage, время отзыва скомпрометированного credential, false trusted-runtime alerts.

**Решение по ФБС.** Сохранить исторический статус «Новая»; инфраструктура доверия, а не самостоятельный кредитный продукт.

## 3.2.6 — Продуктовая аналитика

**Исходный тип:** Доработка. **Идея из HTML:** Анализ трафика, созданного агентами. **Роль в GitHub:** B. **Редакционное действие:** Измерять экономику, не трафик.

**Прикладной сценарий 2031–2036.** Аналитика показывает путь агентного запроса от котировки до подписанного банковского обязательства с выбором конкурирующей оферты.

**Ценность корпоративному клиенту.** Клиенту — понятная стоимость и причины отказов; бизнесу — прозрачность предложения.

**Банковский эффект.** Банк видит contribution после рисков, затраты на подтверждение и потерянную долю платежей.

**Граница и негативный тест.** Не считать A2A calls банковской выручкой; bias по сегментам и коррелированные контрагенты, персональные данные.

**Проверяемые показатели (без вымышленных чисел).** RAC на исполненную сделку; доля выигранных RFQ, adverse selection, cost per verified transaction.

**Решение по ФБС.** Доработка аналитики; необходима и при human approval.

## 3.3.3 — Поддержка продаж

**Исходный тип:** Доработка. **Идея из HTML:** Машиночитаемые описания продуктов и структурированный каталог предложений. **Роль в GitHub:** C. **Редакционное действие:** P0: binding-quote канал.

**Прикладной сценарий 2031–2036.** Агент запрашивает сравнимые котировки по guarantee/escrow/financing с рисковыми требованиями, сроком действительности, различием indicative/binding.

**Ценность корпоративному клиенту.** Компания видит реальную стоимость и условия без неявных комиссий.

**Банковский эффект.** Банк сохраняет участие в выборе финансовых инструментов автоматизированными покупателями.

**Граница и негативный тест.** Не гарантировать доступный лимит до риск-одобрения; не превращать support sales в аукцион, если это не предусмотрено.

**Проверяемые показатели (без вымышленных чисел).** Quote-to-bind conversion; net margin выбранных сделок; expired quote misuse; lost bid reasons.

**Решение по ФБС.** Исходная доработка; высокая стратегическая роль C/P0 — не отдельный денежный продукт.

## 3.5 — Управление историей взаимодействия с клиентами

**Исходный тип:** Доработка. **Идея из HTML:** Machine customers: агенты как отдельный класс клиентов и история их взаимодействий. **Роль в GitHub:** B. **Редакционное действие:** История действий агента ≠ новый клиент.

**Прикладной сценарий 2031–2036.** Хранить цепочку запросов агента, человеческих подтверждений, версий оферт, отказов, ссылок на юридические события и итогов.

**Ценность корпоративному клиенту.** Юрлицо может восстановить, почему операция состоялась, и оспорить ошибку сервиса.

**Банковский эффект.** Банк сокращает сроки расследования и дублирующих обращений.

**Граница и негативный тест.** Раздельная история по тенанту; ретенция/удаление и законный доступ, чужие агентные переговоры не писать без основания.

**Проверяемые показатели (без вымышленных чисел).** Время расследования; процент воспроизводимых решений; полнота trace; жалобы на недоступность истории.

**Решение по ФБС.** Доработка CRM/контактной истории, не новый класс клиентов-агентов.

## 3.8 — Обработка обращений клиентов

**Исходный тип:** Доработка. **Идея из HTML:** Agent-first контактный центр, контроль качества обращений от агентов. **Роль в GitHub:** C. **Редакционное действие:** Поддержать обращение клиента без арбитража.

**Прикладной сценарий 2031–2036.** Если агент по мандату ошибочно инициировал банковскую операцию, клиент подаёт обращение с trace, мандатом и статусами платежа; банк классифицирует банковскую проблему.

**Ценность корпоративному клиенту.** Быстрее разрешает спор о собственном банковском обслуживании.

**Банковский эффект.** Банк снижает ручной cost-to-serve и количество нерешённых кейсов.

**Граница и негативный тест.** Спор buyer–supplier по качеству товара не становится банковским судом; полномочия эскалации и сроки по регуляторике сохранять.

**Проверяемые показатели (без вымышленных чисел).** SLA расследования обращения; доля ошибочно выданных компенсаций; повторные обращения.

**Решение по ФБС.** Исторически Доработка; исследовательская роль C→B предложена только для агентной надстройки.

## Внешние опоры и ограничения переноса

- [Visa/BILL/Billtrust, 20.10.2026](https://investor.visa.com/news/news-details/2026/Visa-BILL-and-Billtrust-Launch-First-Live-Pilot-for-Trusted-AI-Agent-Payments-Between-Buyer-and-Supplier-Platforms/default.aspx) — действующий пилот оплаты **уже одобренных** инвойсов: аутентификация агента не равна праву заключать банковский кредит.
- [BCG Global Payments Report, 23.09.2026](https://www.bcg.com/publications/2026/ai-agents-reshaping-corporate-treasury) — угроза утраты банком клиентского канала; это прогноз экспертов, а не измерение доли Сбера.
- Для изменяемых прав требуются юридически утверждённые корпоративные мандаты; договор и клиент остаются привязаны к юрлицу. Все названные метрики — **предложения для измерения**, не полученные факты.
