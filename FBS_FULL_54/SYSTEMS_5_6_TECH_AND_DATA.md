# Системы 5 и 6 — технология, данные и доверенный обмен: все 11 ФБС

**Основа:** [исходные статусы 54](../TRACEABILITY_54_BASELINE_VS_RESEARCH.md). **Система 5:** 4 доработки + 2 без изменений; **система 6:** 5 доработок. Исторические статусы неизменны, рекомендации 2031–2036 — гипотезы. Технологические процессы не объявляются финансовым продуктом сами по себе.

## 5.1.3 — Разработка ПО

**Исходный статус:** Доработка. **Идея HTML:** Сборка, версионирование, sandbox-среда для A2A-разработки. **Исследовательская роль:** B. **Выбор:** Встроить тестируемую agentic security в жизненный цикл ПО.

**Сценарий 2031–2036.** Банк создаёт изолированный стенд для A2A-интеграций с эталонными заявлениями агентов, поддельным инвойсом, отзывом мандата, подменой инструмента и конфликтом документов.

**Польза для компании.** Команды быстрее интегрируют решения без выхода в продуктив и открытия боевых секретов.

**Эффект для банка.** Снижается риск выпускать ПО с ошибкой авторизации и потерь на инцидентах.

**Риски, предел и негативный тест.** Prompt-injection в документах клиента, tool spoofing, fake EDI, agent collusion; разработчик не может оценивать сам себя по единственной тестовой выборке.

**Метрика или критерий приёмки (предложение).** Security regression pass, воспроизводимость траекторий, escaped critical issues, time to fix.

**Вердикт.** Исходная Доработка/B; банка business product не создавать, а внедрить release gate в SDLC.

## 5.1.5 — Развертывание ПО

**Исходный статус:** Доработка. **Идея HTML:** Деплой и версионирование агентов, healthcheck, откат. **Исследовательская роль:** B. **Выбор:** Надёжные версии, ротация доверия, emergency stop.

**Сценарий 2031–2036.** Каждый релиз A2A-сервиса банка проходит signed artifact, canary на тестовых контрагентах и проверку совместимости схем/прав; при инциденте выполняется отзыв ключей и отключение опасной операции.

**Польза для компании.** Клиент не теряет доступ и видит достоверный статус банковского запроса при обновлении агента.

**Эффект для банка.** Снижение аварийных релизов, ошибочных переводов и стоимости отката.

**Риски, предел и негативный тест.** Rollback кода не откатывает юридически окончательный платёж; оценивать миграции схемы и совместимость ранее выданных мандатов.

**Метрика или критерий приёмки (предложение).** MTTR, canary detection lead, invalid-token rejection, backward compatibility failures.

**Вердикт.** Исходная Доработка/B; deployment ownership и отзыв прав отдельно от клиентского мандата.

## 5.2.6 — Управление мониторингом

**Исходный статус:** Доработка. **Идея HTML:** Мониторинг агентов. **Исследовательская роль:** C. **Выбор:** Мониторить техническую каскадность, а не самовольно решать кредитный риск.

**Сценарий 2031–2036.** Платформа обнаруживает аномальную последовательность вызовов: миллион повторных RFQ, повторные выплаты, рост latency проверок, массовый отказ смежного банка.

**Польза для компании.** Компания раньше узнаёт об ограничении и получает безопасную ручную альтернативу.

**Эффект для банка.** Банк ограничивает IT incident blast radius и потерю STP.

**Риски, предел и негативный тест.** Не считать технический threshold кредитным risk appetite; учёт коррелированной экспозиции принадлежит уполномоченной риск-функции вне среза; false positives не должны массово замораживать легитимные платежи.

**Метрика или критерий приёмки (предложение).** p99 latency, alert precision/recall, stop success, MTTR, correlated retry rate.

**Вердикт.** Исходная Доработка/C, приоритет эксплуатационного kill-switch.

## 5.3.2 — Создание технологической инфраструктуры

**Исходный статус:** Без изменений. **Идея HTML:** —. **Исследовательская роль:** 0. **Выбор:** Исходно БЕЗ ИЗМЕНЕНИЙ; инфраструктура как зависимость.

**Сценарий 2031–2036.** В рамках обычного capacity planning учитывать вычислительные нагрузки агентного шлюза, внешних API и трассировки, не предлагая «новый банковский процесс GPU».

**Польза для компании.** Клиент получает SLA обычной платформы.

**Эффект для банка.** Банк планирует ёмкость и стоимость вычислений без раздувания агентных продуктов.

**Риски, предел и негативный тест.** Не переносить решение о покупке GPU/датацентра в новую продуктовую ФБС; применяются обычные ИБ и устойчивость.

**Метрика или критерий приёмки (предложение).** Capacity utilisation, cost per safe transaction, capacity incidents.

**Вердикт.** NO ADDITIONAL FBS CHANGE; исторически Без изменений, 0.

## 5.3.3 — Обслуживание технологической инфраструктуры

**Исходный статус:** Без изменений. **Идея HTML:** —. **Исследовательская роль:** 0. **Выбор:** Исходно БЕЗ ИЗМЕНЕНИЙ; штатная эксплуатация.

**Сценарий 2031–2036.** Поддерживать резервирование сетевых каналов, платформы и инфраструктурных сервисов по обычным правилам, с агентными требованиями как потребителями SLA.

**Польза для компании.** Нет дополнительных простоев по причине «нового типа клиента» при наличии обычной устойчивой инфраструктуры.

**Эффект для банка.** Стоимость поддержки контролируется действующей эксплуатационной архитектурой.

**Риски, предел и негативный тест.** Не придумывать отдельную «инфраструктуру агентов» для каждого банковского сервиса; необходимы проверка failover и отказоустойчивости в существующем контуре.

**Метрика или критерий приёмки (предложение).** Availability, recovery objective, стоимость обслуживания на транзакцию, отказ при деградации.

**Вердикт.** NO CHANGE; исторически Без изменений, 0, но инженерные тесты остаются.

## 5.4.1 — Управление предоставлением сервисов платформы

**Исходный статус:** Доработка. **Идея HTML:** MCP/A2A gateway: единая точка подключения агентов к инструментам и данным. **Исследовательская роль:** C. **Выбор:** P0: платформа доступа к инструментам.

**Сценарий 2031–2036.** Банковский gateway предоставляет каталог разрешённых API для сравнения оферты/проверки статуса/исполнения, проверяет corporate principal+мандат, делает rate limit, versioning, trace.

**Польза для компании.** Корпоративные разработчики интегрируют один согласованный интерфейс вместо ad hoc логинов.

**Эффект для банка.** Банк удерживает машинный канал и снижает cost-to-integrate для подключаемых партнёров.

**Риски, предел и негативный тест.** Нельзя доверять произвольным MCP-серверам; проверить SSRF, tool-scope, MITM, confused-deputy, prompt-injection через tool results; gateway не решает кредитный риск.

**Метрика или критерий приёмки (предложение).** Validated agent calls, on-boarding time, authorization bypass tests, outage impact.

**Вердикт.** Исходная Доработка/C; это управляемая платформа, не сама доходная ставка.

## 6.1.5 — Управление интегрированными данными

**Исходный статус:** Доработка. **Идея HTML:** RAG, memory, версии документов, права доступа и происхождение данных. **Исследовательская роль:** C. **Выбор:** Граф юридических обязательств с раздельным provenance.

**Сценарий 2031–2036.** По одному deal_id связывать order, counterparty, contract version, invoice, claim, assignment, evidence, guarantee, payment, dispute, не объединяя разные обязательства в «одну сумму».

**Польза для компании.** Клиенту доступна история исполнения и разрешённое подтверждение статуса его требований.

**Эффект для банка.** Банк получает проверяемую основу для контроля double financing и оценки риска, но не доказательство прав сам по себе.

**Риски, предел и негативный тест.** Граф событий не создаёт требования между tier-2 и anchor; разделять inferred и legally verified edges; утечка коммерческих цепочек.

**Метрика или критерий приёмки (предложение).** Verified linkage coverage, erroneous obligation joins, false-positive duplicate finance.

**Вердикт.** Исходная Доработка/C; main data foundation для A1/A2/A3.

## 6.1.6 — Сбор данных

**Исходный статус:** Доработка. **Идея HTML:** Права, качество и происхождение данных в новом объёме для агентов. **Исследовательская роль:** C. **Выбор:** Собирать независимые подтверждения, а не просто подписи.

**Сценарий 2031–2036.** После оплаты или поставки банк получает минимально необходимые ЭДО/ERP/логистические факты и отмечает issuer, signature, contract linkage, независимость инспектора и версию.

**Польза для компании.** Компании меньше представляют повторные бумаги и быстрее получают банковский продукт.

**Эффект для банка.** Банк снижает часть операционной проверки и ложных payout при действительно независимом сигнале.

**Риски, предел и негативный тест.** Подпись поставщика подтверждает автора заявления, не факт доставки; фейковый акт, аффилированный инспектор, backdated documents, revocation.

**Метрика или критерий приёмки (предложение).** Accepted verified events, contradictory events, false approval after negative evidence, verification unit cost.

**Вердикт.** Исходная Доработка/C; только input evidence, не автоматический кредитный approval.

## 6.1.7 — Трансформация данных

**Исходный статус:** Доработка. **Идея HTML:** Права, качество и происхождение данных в новом объёме для агентов. **Исследовательская роль:** B. **Выбор:** Семантические противоречия до выплаты.

**Сценарий 2031–2036.** Сверить суммы, единицы, налог, валюту, даты и версию акта между ERP, эскроу-договором и переводом; конфликт направлять уполномоченному проверяющему.

**Польза для компании.** Меньше ошибок из-за разных форматов систем покупателя и поставщика.

**Эффект для банка.** Банк сокращает расхождения, ошибочные распоряжения и ручные повторные сверки.

**Риски, предел и негативный тест.** Не чинить сумму LLM-галлюцинацией; исходный файл и уверенность трансформации должны сохраняться; quarantine сомнительных случаев.

**Метрика или критерий приёмки (предложение).** Mismatch rate, false auto-correction, time to reconcile, client disputes.

**Вердикт.** Исходная Доработка/B; сильный cost-to-serve challenger при низкой автономии рынка.

## 6.1.10 — Распространение данных

**Исходный статус:** Доработка. **Идея HTML:** Распространение данных, доступных агентам. **Исследовательская роль:** B. **Выбор:** P0 кандидата: безопасное распространение доказательств.

**Сценарий 2031–2036.** Компания разрешает банку поделиться с конкретным контрагентом булевым статусом оплачено/не оплачено и подтверждением источника вместо полного договора; access scoped to mandate.

**Польза для компании.** Коммерчески чувствительные данные не раскрываются всем банкам и торговым контрагентам ради проверки одной поставки.

**Эффект для банка.** Банк может участвовать в доверенной межфирменной сети без несанкционированного раскрытия, защищая trade-finance отношения.

**Риски, предел и негативный тест.** 3.1.10 — правовое основание/согласие, 6.1.10 — фактическая правомерная выдача; 6.1.11 — совместимый формат; revoke нельзя интерпретировать как отмену уже совершённой передачи.

**Метрика или критерий приёмки (предложение).** Unauthorized disclosure count, fields disclosed per purpose, legitimate access completion, audit replay.

**Вердикт.** Исторически Доработка, GitHub B; критический B→C для межфирменной сети — предмет владельца ФБС.

## 6.1.11 — Интеграция и интероперабельность данных

**Исходный статус:** Доработка. **Идея HTML:** Права, качество и происхождение данных для агентских сценариев. **Исследовательская роль:** C. **Выбор:** Интероперабельность статусов сделки, а не один JSON.

**Сценарий 2031–2036.** Согласовать machine semantics заказ/акцепт/денежное требование/уступка/акт/eBL/платеж/спор между корпоративными ERP, банками и партнёрами с явным правовым статусом.

**Польза для компании.** Компании интегрируют разные платформы без ручного перевода существенных условий сделки.

**Эффект для банка.** Банк уменьшает STP exceptions и поддерживает межбанковский агентный бизнес.

**Риски, предел и негативный тест.** Два JSON с одинаковым полем deliveryStatus могут иметь разные правовые значения; нужен authority и mapping version; eBL стандарты не гарантируют межплатформенное право.

**Метрика или критерий приёмки (предложение).** Cross-system matching rate, schema drift alerts, exception resolution time, legal-state confusion.

**Вердикт.** Исходная Доработка/C; ICC 2026 фиксирует фрагментацию eBL как реальную проблему.

## Источники для проверки сценариев

- [BIS Project Agenti, 14.10.2026](https://www.bis.org/node/87745): исследование моделирования агентного влияния на внутридневную ликвидность и шоки — проект, **не** доказательство произошедших убытков.
- [ICC/FIT Alliance eBL Survey, 21.10.2026](https://iccwbo.org/news-publications/news/electronic-bill-of-lading-adoption-grows-as-focus-shifts-to-interoperability/): межплатформенная совместимость — ключевая проблема электронной торговли; **не** доказательство достоверности конкретного отгрузочного акта.
- [BCG Global Payments 2026](https://www.bcg.com/publications/2026/ai-agents-reshaping-corporate-treasury): исключения/расследования/legacy constraints; прогноз и отраслевые наблюдения, не оценка конкретного КИБ.
