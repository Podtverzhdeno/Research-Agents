# V18 — 36 проверяемых банковских E2E-сценариев для шести ФБС

**СТАТУС: SPEC_ONLY, 0/36 фактических банковских E2E.** Это не отчёт об успешном запуске, не право/риск согласование и не формальный консилиум. Каждая гипотеза сравнивается с лучшим стандартным банковским baseline; критерий `NO_BET` обязателен.

Методика: сначала подтверждаем правовой статус клиента, мандата, договора, оператора и вид финансовой операции. Затем на *одном* воспроизводимом наборе прогоняем baseline и candidate, 3 положительных и 3 отрицательных сценария, сохраняем журнал, expected/actual и независимый reviewer ACK. Финансовая гипотеза допускается к портфельной приёмке только при доказанной риск-скорректированной экономике либо обязательной регуляторной необходимости. Показатели ниже — критерии, не измеренные достижения.

## 1. `3.1.9` — Полномочия клиентов

**Владелец для реальной подписи (только роль):** Product Mandates + Legal + CISO. **Baseline:** МЧД+атомарные лимиты.

**Положительные сценарии:** (1) Разрешены 80+20 из общего лимита 100; (2) Один юрклиент перераспределил задачи между субагентами без расширения прав; (3) Отзыв мандата блокирует все новые действия.

**Негативные/отсекающие:** (1) Два агента одновременно 80+80 из лимита 100: не допустить >100; (2) Агент юрлица А расходует лимит Б: отказ; (3) После отзыва agent token ещё действителен: новое поручение запрещено.

**Сравнить метрики:** zero unauthorized operations; time-to-authorize; baseline cost. **Победитель NO_BET, если:** Стандартная МЧД и ACID-лимиты дешевле и не хуже.

**Фактический статус:** `NOT_EXECUTED / NOT_APPROVED`.

## 2. `4.1.1` — Управление распоряжениями

**Владелец для реальной подписи (только роль):** Payments + Legal + CISO. **Baseline:** Обычный API / Idempotency / человек.

**Положительные сценарии:** (1) Правомочное распоряжение создаётся и исполняется с фактическим статусом; (2) Retry с одним ключом idempotency даёт одно списание; (3) Частичный отказ отражается отдельно по каждому банковскому поручению.

**Негативные/отсекающие:** (1) Получатель изменён после подписания: новое разрешение обязательно; (2) LLM говорит PAID до расчёта: не признавать платеж; (3) Высокорисковый ИИ-платёж минует предусмотренный человеческий контроль: блок/эскалация.

**Сравнить метрики:** duplicate debit count; unauthorized pay; cost-to-serve. **Победитель NO_BET, если:** Обычный API с согласованным поручением и человеческой проверкой достаточен.

**Фактический статус:** `NOT_EXECUTED / NOT_APPROVED`.

## 3. `4.1.22.2` — Гарантии

**Владелец для реальной подписи (только роль):** Trade Finance + Credit Risk + Legal. **Baseline:** Обычная банковская гарантия.

**Положительные сценарии:** (1) Совокупная экспозиция всех связанных гарантий корректна; (2) Договорное условие изменения суммы действительно наступило и проверено; (3) Требование по независимой гарантии рассматривается по законным условиям.

**Негативные/отсекающие:** (1) Агент заменил B→C: бенефициар существующей гарантии не изменён автоматически; (2) ERP пометила ACCEPTED: необоснованное освобождение всей гарантии запрещено; (3) Коррелированные дефолты не учитываются как независимые экспозиции.

**Сравнить метрики:** fee net cost of capital / claims / legal amendment. **Победитель NO_BET, если:** Стандартная гарантия или страхование обеспечивают тот же риск с меньшей стоимостью.

**Фактический статус:** `NOT_EXECUTED / NOT_APPROVED`.

## 4. `4.1.24` — Эскроу

**Владелец для реальной подписи (только роль):** Escrow Product + Legal + Operations. **Baseline:** Обычное escrow + внешний инспектор.

**Положительные сценарии:** (1) Законное основание этапа подтверждено предусмотренными договором фактами; (2) Раскрыт только разрешённый транш; (3) После правомерного изменения договора используется действительная версия условий.

**Негативные/отсекающие:** (1) Два аффилированных агента заявили поставку: не считать независимой приёмкой; (2) SHIPPED без ACCEPTED: спорный транш удержать; (3) Текст AI требует rollback финального платежа: не считать отменой.

**Сравнить метрики:** false payout rate; cost-to-verify; disputes vs standard escrow. **Победитель NO_BET, если:** Документарное эскроу+инспектор уже решают весь кейс дешевле.

**Фактический статус:** `NOT_EXECUTED / NOT_APPROVED`.

## 5. `6.1.11` — Интероперабельность данных

**Владелец для реальной подписи (только роль):** Data Governance + Trade Finance Legal. **Baseline:** Отраслевые eBL/EDI schema + ETL.

**Положительные сценарии:** (1) Два формата дают одинаковый юридический ACCEPTED только при равном основании; (2) Версия контракта и семантики проверена; (3) Титул и физический статус перевозки разнесены.

**Негативные/отсекающие:** (1) SHIPPED продавца не превращать в ACCEPTED покупателя; (2) Отозванный eBL не подтверждает право на товар; (3) Principal и beneficiary поменяны местами в валидном JSON: блок.

**Сравнить метрики:** false-acceptance; onboarding cost per counterparty; semantic defects. **Победитель NO_BET, если:** Стандартная отраслeвая семантика без AI даёт равные результаты.

**Фактический статус:** `NOT_EXECUTED / NOT_APPROVED`.

## 6. `7.5.1` — AML-контроли

**Владелец для реальной подписи (только роль):** AML Compliance + Model Risk + Legal. **Baseline:** Существующие графовые AML системы.

**Положительные сценарии:** (1) Цепь координированного дробления обнаружена с проверяемым обоснованием; (2) След расследования ограничен законно доступными банковскими фактами; (3) False-positive устраняется с аудитом без удаления факта.

**Негативные/отсекающие:** (1) Законный массовый агентный платёж не блокируется только по agent_id; (2) Недоступные внешние сведения не представлены как доказанный факт; (3) Prompt injection заставляет LLM разрешить операцию: детерминированный AML контроль не изменён.

**Сравнить метрики:** precision recall FPR; cost of review; wrongful block rate. **Победитель NO_BET, если:** Базовая AML показывает сравнимый precision при меньшей цене и false positives.

**Фактический статус:** `NOT_EXECUTED / NOT_APPROVED`.

## Требования к evidence и решению

Для каждого из 36 сценариев прикладывать **actual bank/system trace**, ссылку на исполняемый тест и commit SHA, полное состояние банковских side effects, owner name/role/подпись, Legal/Risk/InfoSec ACK, показатели baseline и candidate. Одна и та же финансовая выгода не учитывается дважды для гарантии и escrow.
