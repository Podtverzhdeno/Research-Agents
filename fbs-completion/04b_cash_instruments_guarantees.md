# ФБС 4.1.13.1–4.1.24 — физическая наличность и финансовые инструменты (10 из 54)

**Источник:** [сверка с исходной картой](../TRACEABILITY_54_BASELINE_VS_RESEARCH.md); **6 доработок, 4 без изменений** в оригинале. Исходные `D/U` сохраняются. Красные флаги в `4.1.13.1`, `4.1.13.2`, `4.1.14.2` означают **переписать гипотезу и спросить владельца**, а НЕ задним числом изменить исходный счёт 40/3/11.

|---|---|---|---|
| `4.1.13.1` / D | **Переписать исходную идею:** только наличные деньги. Возможный агентный кейс — уполномоченный агент сети магазинов прогнозирует запрос наличности и подаёт заявку банку в заданных лимитах; никакого FX/stablecoin/wallet. | Есть подтверждённый физический cash-flow и банк принимает/отвергает заявку по кассовому лимиту; если такого CJM нет — предложить D→U владельцу. | SOURCE_CONFLICT: старая привязка к цифровой ликвидности отвергнута. |
| `4.1.13.2` / D | **Переписать:** агент инкассируемой организации планирует разрешённую заявку на физический вывоз/приём наличных, проверяет статус маршрута и акт передачи. | Заказ инкассации связан с объектом, доверенным лицом, маршрутом, лимитом и реальным актом приёмки; если нет спроса — D→U на рассмотрение. | SOURCE_CONFLICT: просто «agent-ready fulfillment» без физической операции не требование. |
| `4.1.13.3` / U | Сохранить действующие правила самоинкассации; отдельную агентную программу не создавать без предъявленного cash-CJM. | Платёж, заявка и квитанция по обычной самоинкассации работают штатно; новые agent-only поля не обязательны. | Физическая наличность, не A2A-ecommerce. |
| `4.1.13.4` / U | Оставить кассовое обслуживание обычным процессом с существующими правилами идентификации и сохранности. | Независимо от агентного канала кассовая операция проходит штатную процедуру; нет самовольного cash release. | Не выдавать «без изменений» за отказ от обязательной банковской функции. |
| `4.1.13.5` / U | Оставить экспертизу и инкассо наличных в существующем физическом процессе. | Проверка подлинности и оформление спорных купюр не изменяются вследствие появления агента в ERP. | Невозможно заменить физическую экспертизу цифровой аттестацией агента. |
| `4.1.13.6.2` / U | Сохранить процессы ответственного хранения ценностей и существующие договорные основания их выдачи. | Физическая выдача ценностей по действующей процедуре не становится разрешённой одним агентным сообщением. | Хранение ценностей не равно agent wallet или депозитной смарт-логике. |
| `4.1.14.2` / D | **Переписать:** только при наличии допустимого выпуска реального финансового инструмента — машина готовит параметры и документы эмиссии для утверждения уполномоченными лицами. | Проверены вид инструмента, эмитент, применимое право и право подписанта; без такого сценария предложить D→U владельцу. | SOURCE_CONFLICT: внешний A2A-договор не является эмиссией финансового инструмента. |
| `4.1.14.4` / D | Для сделок с настоящими финансовыми инструментами/хеджем принимать ограниченные мандатом заявки с предторговыми лимитами, котировкой, сроком и отдельным заключением договора. | При превышении полномочия сделка блокируется; по разрешённой сохраняются котировка, сторона, инструмент и банковский риск. | FX/казначейство не всегда относятся к этой ФБС; не подменять их обычным A2A contracting. |
| `4.1.22.2` / D | Разработать различающиеся CJM гарантий оплаты покупателем и исполнения поставщиком: конкретные principal/beneficiary, фиксированные условия выплаты, этапное изменение суммы только по заранее указанным правилам. | Неподтверждённый триггер и несоответствующее требование не меняют/не исполняют гарантию; права бенефициара сохранены. | ГК 368(4) уже допускает событийную сумму; новизну проверять на снижении риска/затрат. |
| `4.1.24` / D | Эскроу в A2A-сделках по проверяемым договорным основаниям; спорный этап удерживать лишь по допустимому договорному порядку, с выбором S0 обычного либо S2 опционального. | False release тест блокируется; этапная выплата реализуется только в отдельно подтверждённой правовой структуре, finality не откатывается. | Премиальный standalone S1 не одобрен без unit economics и правовой проверки. |

## Позиции для решения владельца

- **CR-CASH-01** `4.1.13.1`: принять новый кассовый сценарий с реальным cash flow **ИЛИ** рекомендовать изменение статуса D→U.
- **CR-CASH-02** `4.1.13.2`: подтвердить физическую заявку на инкассацию от агента **ИЛИ** D→U.
- **CR-SEC-03** `4.1.14.2`: указать конкретный эмитируемый инструмент и юридического владельца **ИЛИ** D→U.
- **CR-COLL-04** `4.1.11`: в [предыдущем блоке](04a_banking_accounts_payments.md) остаётся U; при реальном пробеле этапного освобождения обеспечения запрашивать отдельную D (не переименовывать независимую гарантию).

**Без реального физического кассового CJM не создавать фиктивную «агентную наличную ликвидность» как FX/stablecoin.**
