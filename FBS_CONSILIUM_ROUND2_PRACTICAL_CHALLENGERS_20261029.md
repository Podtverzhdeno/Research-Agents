# Раунд II — конкурирующие прикладные идеи по 54 ФБС (29.10.2026)

**Исследовательская дискуссия:** после `100×54` тестирования не повторяем тот же набор фраз, а предлагаем **по одной новой альтернативе к каждой ФБС** и проверяем, не пропущена ли более полезная банковская услуга. 54 индивидуальных новых предложения с контраргументом, модераторским решением и проверкой оформлены отдельным архивом, переданным пользователю в разговоре. Этот файл — **короткое управленческое решение в GitHub**, не полное содержимое архива и не утверждение банка.

## 1. Ключевое изменение: гарантии — не безусловный первый продукт

Три различных критерия дают **трёх различных кандидатов**:

| Назначение | ФБС / конкретный банковский результат | Условное исследовательское решение | Проверка, способная опровергнуть |
|---|---|---|---|
| Быстрый тест оплаты уже разрешённого счёта | `4.1.8.1` — виртуальный корпоративный credential для одобренного инвойса, в пределах лимита/поставщика/срока | Рассмотреть как первый **клиентский UX/E2E** | Существующая карта/ДБО решает задачу дешевле; merchant binding не поддерживается; fraud/retries |
| Банковский доходный продукт | `4.1.22.2` — выпущенная гарантия по агентной заявке через ERP с полноценной проверкой риска, договора и подписанта | Сохранять лидерство в **доходной продуктовой гипотезе**, но не обещать ROI | `Δ risk-adjusted contribution ≤0` к обычной гарантии с учётом капитала, стоимости риска и андеррайтинга |
| Долгосрочный контроль клиентского денежного опыта | `4.1.12` — разрешённый просмотр/операция по счетам **того же юридического лица в других банках** | Read-only discovery с одним партнёром, transfer — позднее отдельным договором | Нет правового доступа/договорного API или клиент не готов платить; каннибализация собственных остатков |
| Юридически сложный способ защиты B2B сделки | `4.1.24` — эскроу с проверкой оговорённого основания выплаты | Отдельный legal-design option, НЕ автоматическая первая волна | Договор не допускает нужного release; инспекция/споры стоят дороже комиссии |

**Не смешивать:** банковская гарантия ≠ залог `4.1.11` ≠ escrow `4.1.24`. Карта под разрешённый инвойс — тоже не кредитная гарантия. Каждый клиентский сценарий должен сравниваться со **своим существующим продуктовым baseline**, а не с абстрактным «ИИ будущего».

## 2. Новизна из внешней практики — точное ограничение

- [Visa/BILL/Billtrust, 20.10.2026](https://investor.visa.com/news/news-details/2026/Visa-BILL-and-Billtrust-Launch-First-Live-Pilot-for-Trusted-AI-Agent-Payments-Between-Buyer-and-Supplier-Platforms/default.aspx): **живой пилот исполнения ранее одобренных B2B-инвойсов** доверенным агентом, не автономный credit underwriting. Для нашей карты означает изучать `4.1.8.1`, `4.1.9.3`, `2.2`, `3.1.9`, а не заявлять, что ИИ изобрёл платежи.
- [Visa Commercial Controls, 21.10.2026](https://investor.visa.com/news/news-details/2026/Visa-Announces-Enhanced-Capabilities-That-Can-Bring-Trust-and-Control-to-the-Future-of-Business-Payments/default.aspx): расширение проверки поставщика/контроля виртуальных корпоративных карт, часть продуктов ещё в пилоте и запуске по странам. Проверять *конкретную поддержку* нашим эмитентом и конкретной карточной схемой.
- [Mastercard AP4M, 10.06.2026](https://www.mastercard.com/europe/en/news-and-trends/press/2026/june/mastercard-launches-agent-pay-for-machines.html): объявленная сервисная программа машинных платежей. **Микроплатёж сам по себе не 2035 breakthrough**; банк должен доказать unit economics.
- [BIS Agorá](https://www.bis.org/project/agora): ограниченные реальные многовалютные тесты в июле 2026, не доказательство универсального B2B Trade DvP или законности расчёта в РФ.

## 3. Дополнительные шесть конкретных разворотов, которые важнее красивых названий

| Бизнес-функция | Контраргумент к прежнему «делаем» | Изменение решения |
|---|---|---|
| `3.1.9` управление полномочиями | Два корпоративных агента могут параллельно тратить один банковский лимит | Условие для запуска: проверяемое **атомарное** распределение мандата на банковское действие, не контроль самой закупки в ERP |
| `3.2.6` продуктовая аналитика | Агент запросил предложение, но клиент оформил гарантию в ДБО — два канала не равны двум продажам | Единый case ID и инкрементальный вклад к контролю, без завышения выручки агентного канала |
| `4.1.5` комиссии | Quote устарел до юридического акцепта, но API показал старую цену | Версионированная стоимость, expiry, новое подтверждение после изменения условий |
| `6.1.7` трансформация данных | ERP поставщика говорит «120 получено», перевозчик — «118 доставлено» | Сначала выделять конфликт и provenance, **не** автоматически «поправлять» документ или раскрывать escrow |
| `5.2.6` IT-мониторинг | Массовые повторы API похожи на атаку, но платёж является законным | IT обнаруживает и ограничивает технический поток по правилам gateway, но не устанавливает произвольную финансовую блокировку |
| `7.7.2.1.3.2` PKI | Внешний сертификат скомпрометирован, банк не является выпускающим CA | Локально перестать доверять credential; не заявлять, что банк отозвал чужой сертификат глобально |

## 4. Что НЕ стоит превращать в отдельные агентные продукты

По реестру `4.1.13.1` — **физическая наличность**, `4.1.13.2` — реальная инкассация, `4.1.13.3–4.1.13.6.2` — кассовая/хранительская физическая работа. `7.2.2.*` — учёт банка, а не факторинг чужих счетов; `5.3.*` — стандартная инфраструктура. Для этих ФБС возможны узкие улучшения (заявка, статус, сверка), но **нет доказанного самостоятельного agent-commerce продукта**.

`4.1.1` — распоряжения на **финансовые инструменты**, не все корпоративные платежи. `4.1.14.2` — **собственная эмиссия банка**, не выпуск бумаг клиентов. `3.3.3` — внутреннее согласование банковских условий, не международный B2B marketplace.

## 5. Что было действительно проверено

- Проанализированы исходные **54 кода** и предыдущие 5 400 модельных записей; подготовлены **54 индивидуальных альтернативных сценария**, по одному на процесс, с возражением, решением и проверкой.
- Покрытие: **54 уникальных ФБС**, исходные **40 «Доработка» / 3 «Новая» / 11 «Без изменений»**, включая `3.1.15`.
- **Не выполнены** банковские E2E, клиентские интервью, расчёт contribution, официальные юридические заключения. Все роли в дискуссии — **аналитические точки зрения одного GPT-6**, не независимые голоса экспертов.
- `3.1.15` находится в исходных 54 и подтверждена пользователем для карты, но отсутствует в приложенной редакции XLSX: официальный паспорт остаётся внешним вопросом.
- Реальный банк-гейт по согласованию находится в [Issue #47](https://github.com/Podtverzhdeno/Research-Agents/issues/47).

**Предложение консилиума:** не голосовать за одного «победителя» до сегментации клиента. Для малого одобренного B2B-инвойса проверить карту; для крупной условной поставки — гарантию; для нескольких банков — внешний кошелёк; для защищённой предоплаты — юридически поддерживаемый escrow. Четыре разных клиентских проблемы, а не четыре competing названия одной идеи.
